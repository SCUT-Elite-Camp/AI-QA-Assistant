## 1. 版本交付结论

本周期完成了从 CP2 Agent 基础能力、普通问答分级路由和 LangGraph 技术验证，到 Local Deep Research 前后端正式接入、对话式交互、执行状态展示、证据核验、报告生成和演示准备的一次完整版本推进。

当前系统具有两条明确分离的产品链路：

```text
普通问答
→ 意图识别
→ 澄清 / 重写 / Query Plan
→ L0 直接回答 / L1 检索回答 / L2 有界多步问答
→ Auto / Deeper / Wider 检索权重

Deep Research
→ 用户显式开启
→ 人工选择本地资料
→ 创建 Research Job
→ 冻结 SourceManifest
→ 动态生成 Research Plan
→ 用户审批或修改
→ Research Graph 有界执行
→ Evidence / Finding / Claim / Verification
→ 生成可引用的研究报告
→ 在同一对话中追问、处理冲突和反馈
```

Deep Research 不会由模型自动触发，不会自动扩展到互联网，也没有替换普通问答主链。

## 3. 普通问答能力

### 3.1 Query Understanding

普通问答主链仍保留以下能力：

```text
用户问题
→ Intent Classifier
→ Follow-up 判断
→ Clarifier
→ Query Rewriter
→ Query Planner
→ Intent Policy Router
→ Agent Runtime
```

系统支持七类意图：

| Intent | 说明 |
|---|---|
| `knowledge_qa` | 知识问答 |
| `document_search` | 文档查找 |
| `summarization` | 内容总结 |
| `comparison` | 多对象或多来源比较 |
| `casual_chat` | 普通闲聊 |
| `system_help` | 系统帮助 |
| `unsupported` | 当前不支持的请求 |

### 3.2 普通问答分级路由

| 路由 | 适用情况 | 执行方式 |
|---|---|---|
| L0 Direct | 闲聊、系统帮助、不支持请求 | 不检索，直接回答 |
| L1 Retrieval | 知识问答、文档搜索、总结 | 单次检索和回答 |
| L2 Bounded Multi-Step | 比较问题或包含子问题 | 有预算限制的多步执行 |

意图识别只在普通 Chat 内选择 L0、L1 或 L2，不能自动创建 Deep Research Job。

### 3.3 Auto / Deeper / Wider

这三个选项是普通问答的检索加权策略，不是三个独立模型模式：

| 模式 | 当前行为 |
|---|---|
| Auto | 默认平衡，Topic 文档加权约为 1.2 |
| Deeper | 更聚焦当前 Topic 已有关联文档，加权约为 1.5 |
| Wider | 降低已有文档偏置，扩大候选范围，加权约为 1.0 |

`Deeper` 当前不是额外推理 Token 或 Deep Research，只是普通问答的“聚焦检索”模式。

## 4. Deep Research 产品目标

Deep Research 的目标不是生成更长的回答，而是针对多资料、复杂比较、版本冲突和高可核验要求的问题，提供：

- 用户可限定的资料范围；
- 用户可审查的研究计划；
- 可观察、可取消、可重试、可恢复的执行过程；
- 从工具结果到 Evidence、Claim 和 Citation 的证据链；
- 不隐藏冲突和资料不足的报告；
- 能够回到原文核验并继续对话的研究体验。

核心价值可以概括为：

```text
资料范围可控
+ 计划经过确认
+ 执行过程可观察和恢复
+ 结论能够追溯原文
+ 冲突能够由用户继续处理
```

## 5. Deep Research 用户完整流程

```text
New Chat
→ 用户选择“深度研究”
→ 选择本地知识库文件
→ 输入研究问题
→ 创建 Research Job，立即返回 research_id
→ 冻结 SourceManifest
→ 动态生成 Research Plan
→ 用户查看计划
   ├─ 批准：开始执行
   └─ 修改：生成新 Plan Version，再次等待审批
→ Durable Dispatcher 领取任务
→ Research Graph 执行
→ 右侧状态栏展示进度
→ 生成最终研究报告
→ 点击引用查看 Evidence 原文
→ 划词提问或继续追问
→ 处理冲突、收藏、赞踩、复制或下载
```

Research 页面底部始终保留输入框。计划审批、计划修改、报告追问和冲突处理均可通过自然语言完成，按钮仅作为快捷入口。

## 6. Source Scope 与本地知识库

### 6.1 用户指定资料

- 用户必须选择至少一份本地知识库文件；
- 前端只提交所选文档的 `document_ids`；
- Job 创建后生成不可变 SourceManifest；
- Approval 绑定 Manifest Hash；
- Planner、Worker 和 Verification 不允许访问 Manifest 外文档；
- 当前不执行 Web Research。

### 6.2 当前存储位置

本地演示环境中的原始文件和知识库均在运行服务的电脑上：

```text
原始或项目文档
D:\htc_qa\agent\docs\...
D:\htc_qa\data-persistence\data\raws\...

处理后的全文与 Chunk
D:\htc_qa\data-persistence\data\documents\<doc_id>.json
```

处理后的 JSON 保存标题、全文、Chunks、原始地址、仓库路径、版本和更新时间等信息。正式服务器部署后，知识库应存放在服务器挂载卷或对象存储中，不一定在终端用户电脑上。

### 6.3 当前用户隔离边界

- Research Job 记录 `user_id`；
- 每个 Job 有独立 SourceManifest；
- 读取工具支持检查文档的 `user_id` 或 `owner_id`；
- 当前部分历史知识库 JSON 没有所有者字段，因此本地目录总体仍接近共享目录；
- 尚未完成完整的用户级 Namespace、权限表和物理隔离。

## 7. Research Plan 与审批

### 7.1 动态计划

`ModelResearchPlanner` 根据研究问题和冻结资料生成 2～5 个任务。每个任务可包含：

- 研究问题；
- 任务目的；
- 依赖关系；
- 允许工具；
- 来源文档；
- Acceptance Criteria；
- 优先级；
- 最大动作次数。

计划必须通过 Schema、Manifest Scope、Tool Allowlist、依赖无环、任务数量和预算校验。

### 7.2 审批规则

```text
Plan v1
→ awaiting_approval
→ 用户批准 plan_version + manifest_hash
→ 保存 Approval Snapshot
→ ready
```

修改计划时：

```text
Plan v1
→ Revision
→ Plan v1 superseded
→ Plan v2 awaiting_approval
→ 用户重新批准 v2
```

当前正式审批点只有 Plan Approval。执行过程中不会逐 Task 暂停审批；报告后的冲突裁决属于结果修订，不是运行中 Graph Interrupt。

## 8. Research Graph 与证据链

### 8.1 Graph 阶段

```text
prepare
→ execute_tasks
→ coverage
→ generate_claims
→ structural_verification
→ semantic_verification
→ render_report
→ finalize
→ completed
```

### 8.2 Worker 约束

- 按 Plan 依赖拓扑顺序执行；
- 只能使用本地只读工具；
- 只能访问 SourceManifest 中的文档；
- 每个任务有 `max_actions`；
- Job 有总 Task、Action、Tool Call、Token 和 Runtime 预算；
- 非法依赖和循环在执行前拒绝；
- 搜索摘要不能直接成为最终 Evidence。

### 8.3 Evidence 链路

```text
Search Hit
→ Observation
→ Read Document Range
→ 扩展命中上下文
→ Original Read
→ Verified Evidence
→ Finding
→ Coverage
→ Claim
→ Structural Verification
→ Semantic Verification
→ Citation
→ Research Report
```

每条 Evidence 至少保存：

- `evidence_id`；
- `research_id`；
- `task_id`；
- `doc_id`；
- `document_version`；
- `locator`；
- `excerpt`；
- `content_hash`。

## 9. 执行状态展示

右侧状态栏读取后端 `ResearchProgress`，不是前端自行模拟。

| 状态 | 对应实现环节 |
|---|---|
| 已创建研究任务 | 创建 Job 并保存请求 |
| 正在生成研究计划 | Planner 生成计划 |
| 等待确认研究计划 | Approval / Revision |
| 研究任务等待执行 | Dispatcher 等待领取 |
| 正在执行研究任务 | Worker 执行 Task 和读取原文 |
| 正在检查资料覆盖度 | Coverage Engine |
| 正在整理研究结论 | Claim Generator |
| 正在检查引用完整性 | Structural Verifier |
| 正在验证研究结论 | Semantic Verifier |
| 正在生成研究报告 | Report Renderer |
| 正在完成研究任务 | Finalize、报告持久化和完成事件 |
| 研究已完成 | Job `completed` 终态 |

前四步属于 Control Plane，中间七步对应 Research Graph，最后一步是终态。

### 9.1 进度百分比

```text
created                  2%
planning                10%
awaiting_approval       15%
ready                   20%
execute_tasks       20%～48%
coverage                58%
generate_claims         68%
structural_verification 76%
semantic_verification   86%
render_report           95%
finalize                98%
completed              100%
```

执行任务阶段根据 `task_completed / task_total` 动态计算，其余数值是用户感知里程碑，不代表准确剩余时间。

## 10. 状态、事件与 Checkpoint 持久化

### 10.1 业务状态数据库

默认位置：

```text
D:\htc_qa\data-persistence\data\research_jobs.db
```

主要数据表：

| 数据表 | 内容 |
|---|---|
| `research_jobs` | Job 状态、当前阶段、Plan 版本和 Manifest Hash |
| `research_manifests` | 冻结资料范围 |
| `research_plans` | Plan 及历史版本 |
| `research_tasks` | Task 和依赖 |
| `research_approvals` | 审批快照 |
| `research_entities` | Evidence、Finding、Claim、Verification、Report 等 |
| `research_events` | 持久化事件流 |
| `research_checkpoints` | 业务恢复位置和实体 ID |

### 10.2 LangGraph Checkpoint

默认位置：

```text
D:\htc_qa\data-persistence\data\research_jobs.db.checkpoints
```

LangGraph `SqliteSaver` 保存 Graph 内部执行位置和游标。业务数据库是权威数据源，Graph Checkpoint 不重复保存完整业务对象。

### 10.3 主要事件

```text
job_created
plan_revised
plan_approved
job_recovered
stage_started
stage_completed
task_started
task_completed
task_failed
task_blocked
report_ready
job_completed
job_failed
job_cancelled
user_message
assistant_message
conflict_resolved
```

事件使用稳定 `event_key` 和唯一约束，避免恢复和重放时重复写入。

### 10.4 恢复流程

```text
服务或页面中断
→ 根据 research_id 读取 Job
→ 读取业务 Checkpoint
→ 校验 Plan Version 和安全恢复阶段
→ 读取 LangGraph Checkpoint
→ 写入 job_recovered
→ 从最后安全阶段幂等恢复
```

页面刷新则重新读取 Job、Plan、Progress、Events 和 Report，不依赖浏览器内存。

## 11. 报告、引用和冲突处理

### 11.1 报告结构

最终报告以普通助手回答形式展示，包含：

- 结论摘要；
- 关键发现；
- 逐项分析；
- 冲突及处理依据；
- 局限和无法确认事项；
- Citation 与 Evidence 原文。

### 11.2 引用交互

- `[1]`、`[2]` 转换为普通问答风格的引用标签；
- 点击文档名称展开该文档第一条 Evidence；
- 点击编号精确切换对应 Evidence；
- 原文在当前对话内展开；
- 长内容支持上下滚动；
- 展示 Locator、版本和更新时间；
- 报告文字支持划词复制和划词提问。

### 11.3 当前完整源文件链接限制

Evidence 原文片段已经能够展示，但“打开来源”暂未完成正式文档服务链路。

当前 `source_url` 可能是仓库相对路径，浏览器会错误解析为 Research 页面下的 URL。正确实现还需要：

```text
GET /api/research/jobs/{research_id}/documents/{doc_id}
→ 校验用户权限
→ 校验文档属于当前 SourceManifest
→ 读取处理后全文或原始文件
→ 返回安全预览
→ 前端定位到 citation.locator
```

该问题属于 Research 文档访问 API/BFF，不需要修改底层检索算法。

### 11.4 冲突处理

系统应展示具体冲突命题、双方原文、版本、更新时间和权威等级。用户可以通过对话：

- 采用指定来源；
- 以最新版为准；
- 保留双方并注明适用范围；
- 继续读取上下文后再判断。

用户决定和理由保存为 `conflict_resolved` 事件，并用于生成报告修订。

### 16.3 当前明确不做

- Web Research；
- 自动将普通问答升级为 Deep Research；
- 并行 Worker；
- 多 Agent 协作；
- SSE / WebSocket；
- Word / PDF 导出；
- 修改底层检索算法。
