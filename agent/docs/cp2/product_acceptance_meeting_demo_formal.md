# CP2 Agent 本周真实 Confluence 测试报告

> 测试日期：2026-09-21  
> 测试性质：开发阶段产品机器预验收  
> 数据依据：[PR #44](https://github.com/SCUT-Elite-Camp/AI-QA-Assistant/pull/44) 中的验收集、执行器、结果说明与修复记录  
> 测试对象：G1 普通问答、G2 Deep Research  
> 注意：本报告不纳入其他全量评测或补充测试结果

## 1. 测试摘要

本周测试的目标，是验证 Agent 面对真实 Confluence 工程资料时，能否给用户提供**正确、完整、受原文支持且不越过资料边界**的回答，而不再只以“接口成功”或“任务 completed”作为通过标准。

测试从冻结的 RAG Confluence 工程文档中选取 7 个代表性问题，同一问题分别经过普通问答和 Deep Research 两条真实 API 链路。测试覆盖单文档事实、多文档比较、跨章节追溯、数字与条件判断、表格空值、无关资料干扰和资料不足拒答。

| 指标 | G1 普通问答 | G2 Deep Research |
|---|---:|---:|
| 测试问题 | 7 | 7 |
| 每题重复次数 | 2 | 2 |
| 当前代码全量运行数 | 14 | 14 |
| 运行成功并通过机器预验收 | **14** | **14** |
| 当前批次机器预验收通过率 | **100%** | **100%** |

两组共完成 **28 次当前代码全量确认**，均达到本测试集的机器规则。修复前单次基线为 G1 4/7、G2 0/7，说明“链路能够运行”与“答案达到产品要求”是两个不同层面。

该结果仅代表固定冻结数据、固定问题及当前验收规则下的开发阶段结果，不代表线上质量、未知问题通过率或最终产品验收。

## 2. 测试目标

本轮测试重点回答以下问题：

1. 普通问答是否能从正确的周次和模块中检索事实并形成直接回答。
2. Deep Research 是否真正完成计划、检索、原文读取、报告生成和引用返回，而不是把检索片段直接拼成报告。
3. 跨文档比较时是否能同时保留两侧证据并正确计算差值。
4. 跨章节问题是否能关联功能提交和受影响代码文件。
5. 表格中的空白值是否会被错误推断为 Finished 或 Not started。
6. 存在相似周报或其他模块数据时，系统是否会混入无关数字。
7. 允许资料不足时，系统是否能明确拒绝精确结论。
8. 引用的文档、chunk 和摘录是否与冻结原文一致。

## 3. 测试对象与真实执行路径

### 3.1 G1：普通问答

G1 通过公开 `POST /api/chat` 接口执行，使用冻结 BM25 索引，并通过 `doc_ids` 限定本题允许访问的文档。

```text
用户问题
  -> 意图识别与策略路由
  -> 查询重写/独立查询
  -> 冻结 BM25 检索
  -> 证据门控与有界纠偏
  -> 基于冻结证据生成回答
  -> 返回直接回答与引用
```

### 3.2 G2：Deep Research

G2 经过完整 Research API 链路：

```text
创建研究任务
  -> 生成研究计划
  -> 批准计划
  -> 按任务执行 Search
  -> 根据 chunk 定位读取原文
  -> 保存 Evidence / Finding / Claim
  -> 检查覆盖度、冲突和资料边界
  -> 生成研究报告
  -> 返回结论、局限、引用与原文位置
```

G2 使用 SourceManifest 限定的本地 JSON 冻结文档执行 Search/Read。本轮没有验证在线 Confluence 同步、真实用户 ACL、Page Index、Milvus 或端到端 hybrid 检索。

## 4. 测试数据与冻结方式

测试资料来自真实 RAG Confluence 工程记录的本地冻结快照。每个用例继承原评测资产中的允许文档 ID、来源版本、内容哈希、关键原文 chunk 和禁止出现的错误结论。

运行前，执行器重新计算本地文档内容哈希并核对 metadata 中的版本。如果与冻结 SourceManifest 不一致，测试直接报 `source drift` 或 `version drift`，避免文档变化后继续使用旧金标准。

这 7 题是针对真实产品风险设计的开发验收集，不是生产用户日志，也不是未见盲测集。其作用是稳定复现并验证已知关键缺陷，而不是估计系统在所有问题上的平均准确率。

## 5. 七个测试用例详细说明

| 用例 | 场景 | 金标准 | 主要风险 |
|---|---|---|---|
| PA-001 | 单文档事实 | W30 Agent：总提交 9、新功能 5、Bug 修复 1、其他改进 3 | 只返回总数或遗漏分类 |
| PA-002 | 跨文档比较 | W30 9/5/1/3；W34 8/3/5/0；变化 −1/−2/+4/−3 | 只召回一周、混淆比较方向 |
| PA-003 | 跨章节追溯 | commit `32559e07a`、`e93c32fbf`、`3d3f27dda`；文件 `rewriter.py`、`clarifier.py`、`intent_classifier.py` | 只读功能章节、漏读文件章节 |
| PA-004 | 数字条件判断 | 5+1=6≥6、1≤1，结论通过 | 复制数字但不计算，或误计其他改进 |
| PA-005 | 表格与空值 | M6/M7/Research Graph M8/M9 Finished；M10 Not started；M11 未记录 | 同 ID 混淆、把空白状态补成推测 |
| PA-006 | 无关资料干扰 | fionaxi、2026-07-25、W30 Agent 总提交 9 | 混入 W28、Master 或 Web 数字 |
| PA-007 | 资料不足/范围约束 | 明确无法确认 W34 Web 精确数字，不用 Agent 数据替代 | 越权读取或编造精确数字 |

### 5.1 PA-002 的数值金标准

| 指标 | W30 | W34 | W34−W30 |
|---|---:|---:|---:|
| 总提交 | 9 | 8 | −1 |
| 新功能 | 5 | 3 | −2 |
| Bug 修复 | 1 | 5 | +4 |
| 其他改进 | 3 | 0 | −3 |

PA-002 是本轮最能体现 Deep Research 价值的用例：系统必须同时读取两份周报、区分时间范围、保留两侧证据、执行计算，并让各项结论引用对应原文。

### 5.2 PA-007 的行为金标准

PA-007 并不要求“找到正确数字”，而是要求系统识别资料范围不足。即使知识库其他位置可能存在 Web 周报，本题允许资料只有目录页与 Agent 归档，因此合格回答必须拒绝给出 W34 Web 的 commits/feat/fix 精确值。

## 6. 评分与通过规则

一次运行只有同时满足以下条件才记为 accepted：

1. **运行成功**：G1 返回 `success` 或合理的 `no_relevant_context`；G2 Job 状态为 `completed`。
2. **逐点检查全部通过**：自动裁判对该题每一条 check 返回 `true`，仅提到关键词或数字不算完成。
3. **Faithfulness ≥ 4/5**：回答必须忠实于冻结原文。
4. **Citation support ≥ 4/5**：引用必须真实支持对应事实，不能只保证编号存在。
5. **越权证据为 0**：Evidence 的 `doc_id` 必须属于该题允许范围。
6. **原文定位有效率为 100%**：Evidence locator 必须存在，excerpt 规范化后必须能在对应冻结 chunk 中匹配。

对于合理拒答，如果没有额外事实断言，可以获得完整 citation-support 评分；系统不应为了“有答案”而编造数字。

### 6.1 自动裁判配置

执行器使用同供应商模型进行逐点机器初筛：`temperature=0`、Thinking 关闭、JSON 结构化输出，只允许依据冻结问题、原文、回答与引用，输出逐点布尔值、faithfulness、citation support 和理由。

该评分属于机器预验收，不是独立人工评价。相同供应商可能存在自评偏差，因此最终结论仍需人工复核。

### 6.2 来源完整性指标

执行器额外记录 Evidence 数量、有效 excerpt 数量、locator/excerpt 有效率、关键原文位置召回率、越权文档数量和响应耗时。关键位置召回率用于定位检索覆盖缺口；accepted 的硬条件仍以逐点事实、忠实度、引用支持、无越权和定位有效为准。

## 7. 测试过程与量化结果

### 7.1 修复前基线

| 组别 | 通过/运行 | 通过率 |
|---|---:|---:|
| G1 | 4/7 | 57.1% |
| G2 | 0/7 | 0% |
| 合计 | 4/14 | 28.6% |

接口均能执行，但大量回答未满足事实完整性、证据覆盖或引用质量要求。该阶段证明：**运行成功不能替代答案质量验收。**

### 7.2 修复后首次全量复跑

| 组别 | 通过/运行 | 通过率 | 剩余失败 |
|---|---:|---:|---|
| G1 | 12/14 | 85.7% | PA-006 两次 |
| G2 | 13/14 | 92.9% | PA-007 一次 |
| 合计 | 25/28 | 89.3% | 3 次 |

剩余问题具有明确定位：

- **PA-006 / G1：**限定文档后的检索候选窗口仍不足，正确 W30 Agent 章节可能被标题、摘要或相似周次挤出。
- **PA-007 / G2：**报告生成仍可能把相邻模块证据带入回答，没有把用户指定模块和允许资料范围作为足够强的结论边界。

### 7.3 定向修复与复跑

| 定向用例 | 组别 | 结果 | 说明 |
|---|---|---:|---|
| PA-006 | G1 | 2/2 | 调整受限文档的有界检索窗口后，作者、日期和 Agent=9 均正确返回 |
| PA-007 | G2 | 2/2 | 强化模块、周期和 Manifest 边界后，两次均拒绝编造 Web 数字 |

定向复跑仅用于确认具体缺陷已经消除，不替换此前的失败记录。

完成定向修复后，再对 7 题、G1/G2、每题 2 次进行独立全量确认：

## 9. 失败原因、修复与效果

| 问题层级 | 修复前问题 | 主要修复 | 验证效果 |
|---|---|---|---|
| 检索 | 只读标题/摘要，漏掉后续章节或另一周资料 | chunk 级候选、同文档多章节读取、结构化标题降权、标识符拆分 | PA-002/003/006 所需事实完整召回 |
| 普通问答 | 证据通过后仍重复检索，比较证据去重丢失一侧 | 证据冻结后进入无工具回答；先保留各查询命中再展示去重 | G1 能稳定形成最终答案和双侧比较 |
| 报告生成 | 报告缺段落、引用或关键结论；相邻模块数据进入结论 | 检查结构、截断和引用编号；一次有界修复；强化模块/周期/Manifest 边界 | G2 最终 14/14，PA-007 正确拒答 |
| 冲突判断 | 不同周次/模块数字不同被误判为来源冲突 | 识别时间与范围差异，把不同数字作为比较输入 | PA-002 正常生成变化结论 |
| 渲染 | 超长冲突材料导致报告渲染失败 | 用户侧摘要限制 2,000 字符，完整内容留在 Evidence/Citation | 避免大表格破坏最终报告 |

## 10. 结果解释与限制

### 10.1 可以得出的结论

- 已建立一套覆盖 7 类真实 Confluence 风险的产品预验收集。
- G1 和 G2 均通过真实产品 API 路径执行，而非只调用内部函数。
- 当前固定验收集两轮共 28 次均达到机器规则。
- 已知的章节遗漏、比较证据丢失、工具重复调用、资料越界和报告结构问题得到修复并复跑确认。
- 系统在 PA-007 中表现出了“没有足够证据时不编造”的能力。

### 10.2 不能由本次测试推出的结论

- 不能据此宣称线上或全项目质量达到 100%。
- 不能推断未知问题也会全部通过。
- 不能宣称真实用户 ACL、在线 Confluence 同步或资料更新流程已通过。
- 不能宣称 Page Index、Milvus 或 hybrid 检索已经验收。
- 不能用 415 项代码测试替代 28 次产品回答测试。

### 10.3 自动评分风险

本轮使用同供应商模型进行逐点预判，存在自评偏差。自动规则也可能只关注预定义检查点，而遗漏回答中的附带错误。

已知案例是 PA-006 的一份 G2 报告曾附带说明“证据未给出 W30 主报告的全项目总提交数”，而允许资料实际记录项目总提交数为 14。该句不影响题目要求的 Agent=9，因此逐点规则仍可判通过。这说明正式产品验收仍需逐篇人工阅读，而不能只看 accepted 字段。

## 11. 本周测试结论

本周完成了从“链路可运行”到“真实问题可验证”的第一版产品预验收闭环：建立 7 题真实 Confluence 验收集，打通 G1/G2 两条端到端路径，记录修复前基线，针对失败完成检索、证据门控和报告链路修复，并执行定向复跑与全量确认。

最终固定集结果为 **G1 14/14、G2 14/14**。该结果证明已知高价值场景在冻结环境下达到机器预验收标准；下一阶段仍需合并后复测、独立人工签字和新增盲测问题。
