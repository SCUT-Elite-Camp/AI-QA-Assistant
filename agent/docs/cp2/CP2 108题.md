## 2. 测试集详细介绍

### 2.1 测试集设计原则

第一版测试集共 18 题，来源于冻结的 RAG Confluence 快照。测试题没有只选择容易命中的普通问答，而是覆盖需要多步检索、跨文档核验、冲突处理、权限控制和引用溯源的真实场景。

每个测试用例都包含：

- `case_id`：稳定的测试编号；
- `question`：用户真实问题；
- `category`：问题类型；
- `expected_behavior`：预期回答、拒答、请求补充信息或冲突复核行为；
- `required_facts`：回答必须覆盖的事实；
- `allowed_document_ids`：允许读取的文档；
- `forbidden_document_ids`：禁止读取的文档；
- `SourceManifest`：文档版本、内容哈希、来源 URL 和权限范围。

这样设计可以区分以下三种情况：

1. 系统没有检索到正确文档；
2. 系统检索到了文档，但没有形成足够证据；
3. 系统拥有正确证据，但最终报告没有正确表达或引用。

### 2.4 SourceManifest 与权限约束

每题的 SourceManifest 不仅限定“可以检索哪些文档”，还用于检查：

- 检索结果是否超出授权范围；
- 引用的文档版本是否与冻结版本一致；
- 文档内容是否发生漂移；
- 来源链接是否指向正确页面；
- 同一问题多次运行时输入条件是否一致。

权限类题目还配置了 `forbidden_document_ids`。只要结果使用禁用文档，即使最终答案正确，也会被判定为硬门槛失败。

### 3.2 六层评测

| 层级 | 评测内容 |
| --- | --- |
| Plan | 是否覆盖问题要求、任务是否重复、依赖是否合理 |
| Retrieval | 正确文档命中、正确章节命中、Evidence Recall@K、噪声比例 |
| Evidence | 是否读取正确原文、上下文是否完整、证据是否充分、冲突是否正确识别 |
| Report | 正确性、完整性、Faithfulness、Answer Relevance |
| Citation | 每个事实断言是否有支持引用、来源链接能否打开、定位是否有效 |
| Runtime | 是否正常完成、是否重试、是否降级、是否从 Checkpoint 恢复 |

Runtime 层用于确认流程是否稳定完成，但本报告不把速度作为主要结论。核心关注点仍是回答是否正确、完整、有证据且可追踪。

### 3.3 硬门槛

以下指标任一失败，即使语义评分较高，该条记录也不能算通过：

- 权限泄漏数必须为 0；
- 断裂引用数必须为 0；
- 无证据事实断言数必须为 0；
- 不可打开来源链接数必须为 0；
- 事实断言引用覆盖率必须为 100%；
- Faithfulness 必须达到要求；
- Answer Relevance 必须达到要求。

这种设计避免“答案看起来不错，但证据链不可核验”的结果被误判为通过。

## 4. 本周完成的系统修复

### 4.1 检索和索引链路

- 恢复本地 BM25 索引，使现有混合检索降级链路可用；
- 排查向量维度与已有 Collection 不一致问题；
- 验证 Milvus、MinIO 和 etcd 服务；
- 将检索失败、文档未命中、章节未命中和无相关上下文分别记录；
- 保留失败运行，不为了提高成功率删除异常数据。

### 4.2 相邻 Chunk 与原文读取

针对只命中标题、单行常量或表格碎片的问题，补充相邻 Chunk 读取：

- Search 命中后继续读取原始文档范围；
- 将相邻上下文写入 Evaluation Trace；
- 保存文档 ID、Chunk locator、版本和内容哈希；
- 为报告生成提供完整上下文，而不是只使用单行命中结果。

### 4.3 Evidence 与报告质量

- 统一将工具结果转换为 Evidence；
- 增加证据充分性和冲突状态字段；
- 检测报告大段复制 Evidence 的情况；
- 对“复制原文但没有综合结论”的报告触发重写或救援生成；
- 保留局限性、无法确认事项和冲突处理结果。

### 4.4 评分稳定性

- 固定评分字段和 JSON 输出契约；
- 校验事实 ID、Claim ID 和分数范围；
- 要求返回已支持事实与无证据 Claim；
- 拒绝逻辑矛盾的评分结果；
- 评审失败时标记 Pending，不保留半解析结果；
- 将语义评分和确定性硬门槛分离，避免链接状态干扰语义判断。

### 4.5 Citation 与 Claim 映射

测试中发现 G2 的真实 Claim ID 为 `claim-finding-*`，而旧转换逻辑将 Citation 绑定到统一的 `report-answer`，导致评分器错误地把全部 G2 引用判为缺失。

已根据 Citation 与 Claim 共同引用的 Evidence ID 重新建立映射。修复后：

- Citation 可以关联真实 Claim；
- 不再出现 54/54 全部由映射错误造成的误判；
- 剩余引用覆盖失败反映的是部分事实断言没有形成明确 Citation 关系，需要继续修复 Evidence 到报告的绑定。

结果说明：

1. **G2 证据召回更高。** Deep Research 能够读取更多与问题相关的证据，说明多步检索和证据收集有实际作用。
2. **G2 完整性低于 G1。** 部分报告虽然拥有更多证据，但没有覆盖问题要求的全部字段，尤其容易遗漏限制条件、具体数字或未确认事项。

4. **G2 相关性仍需优化。** 报告结构更长、信息更多，但部分内容偏离用户直接问题，导致 Answer Relevance 下降。
5. **“找到更多证据”尚未稳定转化为“生成更好的报告”。** 当前主要瓶颈已经从检索阶段转移到 Evidence→Claim→Citation→Report 的组织阶段。

### 5.7 本轮测试反映的核心问题

本轮结果可以归纳为四个核心问题：

1. **Deep Research 能找到更多资料，但证据利用率不高。** Evidence Recall@K 提升，报告完整性却没有同步提升。
2. **Citation 覆盖是当前最大阻塞。** 来源链接可用不等于引用完整，需要让每个事实 Claim 都有明确 Evidence 和 Citation。
3. **复杂报告容易遗漏用户约束。** 多文档、冲突、范围歧义和信息不足场景中，报告容易漏掉限制条件或未确认事项。
4. **冲突识别需要从“来源不同”升级到“命题真正矛盾”。** 标题、日期或适用范围不同不应直接判为冲突。

## 10. 总结

本周已经完成 Deep Research 的第一版效果基线和完整评测闭环。结果表明，Deep Research 在证据召回方面具备优势，但尚未稳定地将更多证据转化为完整、直接、逐断言可引用的研究报告。

下一阶段应优先修复 Evidence→Claim→Citation→Report 链路，而不是盲目增加流程复杂度。只有当每个事实都能定位到证据、每条引用都能支持具体断言、信息不足时能够克制拒答，Deep Research 才能真正体现相较普通问答的可靠性价值。
