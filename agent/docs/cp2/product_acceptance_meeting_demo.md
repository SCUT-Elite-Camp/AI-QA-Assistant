# 周会展示：用真实 Confluence 问题验收 Agent 的回答

> 2026-09-21 本地结果｜建议讲述 5 分钟｜本稿可直接投屏

## 先说结论

**我们正在做的事：**从真实 Confluence 工程文档的冻结快照中选出 7 个代表性用户问题，给每题规定正确答案和应读的原文位置；让同一题分别走普通问答和 Deep Research，再逐题检查回答与证据。

**它的用处：**以前只能证明“接口跑通、任务完成”；现在能发现“找到了文档却没读对章节、比较时混了周次、表格空白被猜成状态、引用不支持结论、资料不足却编出数字”等用户真正会遇到的问题。

**当前状态：**在这 7 题上，当前本地代码两轮机器预验收为 **G1 14/14、G2 14/14**；修复前单轮分别为 **4/7、0/7**。这是有边界的开发结果，**尚未经过独立人工签字，也不是线上产品验收通过**。

## G1、G2 到底是什么？

| | G1：普通问答 | G2：Deep Research |
|---|---|---|
| 用户操作 | 提问，等待一次回答 | 提问，确认研究计划，等待研究报告 |
| 本次测试路径 | POST /api/chat | 创建研究 → 生成计划 → 批准 → 执行 → 获取报告 |
| 期望产物 | 直接回答问题，附可追溯证据 | 分步骤查资料，形成有引用的完整报告 |
| 本次资料读取 | 冻结 BM25 索引 | 限定文档范围的本地 JSON Search/Read |
| 不是 | “简单题”或低分组 | “高级评分”等级；也不是线上 Confluence 同步测试 |

**关键点：同一道真实问题同时测 G1 和 G2。**我们不是比较谁写得更长，而是看两条产品路径能否给出同样正确、受原文支持的结论。G2 还要检查报告结构、跨章节阅读和引用。

## 7 个真实问题：G1/G2 实际怎么回答？

以下是当前完整复跑中每题第 1 次的**回答要点摘要**，不是预设的理想答案；第 2 次也达到机器验收门槛。完整原文与运行记录见文末。

| 题目与用户需求 | G1 普通问答实际回答 | G2 Deep Research 实际回答 |
|---|---|---|
| **PA-001｜查事实**<br>“W30 Agent 的总提交、新功能、Bug 修复、其他改进各是多少？” | 直接给 **9 / 5 / 1 / 3**，引用周报，并用 9 条提交明细交叉核对。 | 报告先给 **9 / 5 / 1 / 3**，再解释“其他改进 3”对应 2 条文档与 1 条维护提交。 |
| **PA-002｜跨周比较**<br>“对比 W30 与 W34 Agent 的四项交付数字及变化。” | 用表格给出 **9/5/1/3 → 8/3/5/0**；按 W34 减 W30 得 **−1/−2/+4/−3**，分别引用两周资料。 | 报告的结论和对照表给出同一组数字及变化，并列出两份周报的具体来源 chunk。 |
| **PA-003｜跨章节追溯**<br>“query rewriter、clarification decision、intent classifier 分别是哪些提交？新增了哪些 Python 文件？” | 给出三项 commit：32559e07a、e93c32fbf、3d3f27dda；再列出 rewriter.py、clarifier.py、intent_classifier.py。同时说明原文未逐提交标注文件映射。 | 报告从 “New Features” 和 “Impacted Code Files” 两个章节取证，列出同样的三项 commit 和三个新增文件。 |
| **PA-004｜算条件**<br>“W30 Agent 的新功能+修复不少于 6，且修复不超过 1，是否通过？” | 取原数 **5、1**，计算 **5+1=6≥6** 且 **1≤1**，结论通过；未把“其他改进 3”算进去。 | 报告做相同的两项判断，并明确排除无关的 3 项其他改进。 |
| **PA-005｜读表格与空值**<br>“核对 CP2 Goals 中指定里程碑状态；空白写‘未记录’。” | AG-M6/M7、Research Graph 那条 AG-M8、AG-M9 为 **Finished**；AG-M10 为 **Not started**；AG-M11 为**未记录**，并指出 AG-M8 有同 ID 的另一条目标。 | 报告列出同样状态，特别区分 Research Graph 的 AG-M8 与 Skill Registry 的 AG-M8，不把空白状态猜成完成。 |
| **PA-006｜抗干扰**<br>“谁在何时提交 W30 Agent query rewriter？该周 Agent 共几次提交？不要混入其他周次/Web。” | **fionaxi，2026-07-25，W30 Agent 共 9 次**；还区分了 W30 全项目的 14 次。 | 结论同为 **fionaxi，2026-07-25，9 次**，没有把 Web 或其他周次数字当成 Agent；一条旁支说明仍待人工复核，见下文。 |
| **PA-007｜证据不足**<br>“我只能看目录页和 Agent 归档；请给 W34 Web 的精确提交及 feat/fix 数。” | 明确说**无法确认 Web 的精确数字**；解释看到的 Agent 数据不能代替 Web 数据。 | 报告逐项写“无法确认”，说明授权资料只有目录与 Agent 归档，**没有编造 Web 数字**。 |

### 现场建议重点讲 PA-002 与 PA-007

PA-002 展示“**有资料时答准**”：同一问题要找到两周的正确章节，算对四项差值，并把引用落到各自原文。PA-007 展示“**没资料时不乱答**”：仓库里即便存在 Web 相关资料，本题限定的文档没有提供 Web 精确数字，回答就必须守住边界。这比只演示一篇漂亮的长报告更能说明产品质量。

## 我们怎样判定“答对”？

每次运行不只看接口是否成功，还同时检查：

1. **事实完整：**题目要求的每个数字、状态、计算或拒答点都答到了。
2. **证据正确：**引用来自本题允许的文档；返回的 chunk 定位和摘录能在冻结原文匹配。
3. **回答可信：**同供应商模型裁判的忠实度和引用支持度均至少 4/5；不得写出题目禁止的数字或推断。裁判结果仍需人工复核。
4. **路径真实：**G1 调公开问答 API；G2 走创建、计划、批准、执行、报告的完整 API 链路，不是单独调用报告生成器。

| 运行批次 | G1 | G2 | 应如何解读 |
|---|---:|---:|---|
| 修复前：7 题 × 1 次 | **4/7** | **0/7** | 证明“链路能跑”不等于“答案合格” |
| 当前本地代码：7 题 × 2 次 | **14/14** | **14/14** | 28 次均运行成功，均达到本套机器规则 |

两批重复次数不同，不能把分数当作线上成功率或统计显著性结论。另有 **415 项代码测试通过**，但那是代码回归，不能代替上述产品回答验收。

## 本轮改动带来了什么？

| 原先用户能看到的缺口 | 对应改进 |
|---|---|
| 找到周报，却只读到标题/摘要，漏掉文件清单 | Research 按 chunk 找证据，允许读取同一文档的多个章节 |
| 比较题两边资料都检索到，但回答只保留一边；相似周次/模块串线 | 保留每个查询的证据来源，调整有界检索窗口与周次识别 |
| 报告完成却缺段落、引用或关键结论 | 检查报告结构、截断和引用编号，不合格时做有界修复 |
| 要 Web 数字，却把 Agent 数字代答 | 把题目指定的模块、时间和资料范围当作硬边界，缺证据就说无法确认 |

## 结论的边界与会议后的动作

**现在可以说：**我们有一套来自真实 Confluence 文档、可重复运行、能追查原文的 Agent 产品**机器预验收集**；当前本地代码在这 7 题的 G1/G2 两轮运行中全部达到预设规则。

**现在不能说：**全项目质量已达标、真实用户的 Confluence ACL 已验证、在线同步或 hybrid 检索已验收、Deep Research 对未知问题也有同样通过率。目前使用的是冻结快照；G2 是限定范围的本地 JSON 检索。代码仍在未提交的本地工作树上。

**人工复核仍然必要。**抽查 PA-006 的一份 G2 报告时，发现它有一句“证据未给出 W30 主报告的全项目总提交数”；而本题允许的 W30 主报告记有项目总提交数 **14**。这句不影响本题要求的 **W30 Agent=9**，所以机器逐点规则没有拦下它，但它说明“14/14”不等于整篇回答零瑕疵。会议上应如实展示并纳入人工审读清单。

下一步按顺序做：**① 非开发者逐题核对回答与原文并签字；② 合并到目标 agent-dev commit 后复跑；③ 扩充未参与本轮修复的真实 Confluence 盲测题；④ 权限具备后补测真实用户 ACL、在线同步和 dev 集成。**
