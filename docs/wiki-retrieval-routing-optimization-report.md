# Wiki 检索路由与证据补充优化汇报

## 1. 优化背景

原有流程主要在 Direct 检索后判断“当前证据是否充足”，再决定是否启动 Wiki。这个方案有三个问题：

- 证据充足性很难在回答生成前稳定判断，容易误触发或漏触发 Wiki。
- Wiki 召回结果如果与 Direct 结果再次竞争同一配额，新发现的有效证据可能仍无法进入最终上下文。
- 对所有问题都启动 Wiki，会带来额外的检索延迟和 Token 成本。

本次优化因此分为两部分：首先由 Agent 在检索前选择是否启动 Wiki；其次将 Wiki 找到的原始证据作为 Direct 证据的受控补充，统一组装后再交给 LLM。

## 2. 优化一：Agent 如何选择检索路由

### 2.1 路由选择不是独立分类器

自动模式下，系统没有新增一次独立的 LLM 分类调用。现有 Agent 在第一次工具选择时，通过“选择哪个入口工具”同时完成检索路由决策：

- 选择 Direct 检索入口，表示当前请求走 `Direct only`。
- 选择 Wiki 搜索入口，表示当前请求走 `Direct + Wiki`。

这样既不需要先召回一次再猜测证据是否足够，也不会为路由单独增加一次模型往返。

### 2.2 Agent 根据什么选择

系统在 Agent 提示中给出两类语义边界：

| 问题特征 | 选择路由 | 目的 |
| --- | --- | --- |
| 精确事实、数字、代码、指定文档或局部片段 | Direct only | 快速获取与问题直接匹配的原始证据 |
| 概念全景、主题关系、跨文档综合或多跳问题 | Direct + Wiki | 先利用 Wiki 扩展发现范围，再回溯原始证据 |

这是基于问题语义的 Agent 选择，而不是一组硬编码关键词规则。

### 2.3 路由选定后如何执行

```text
用户问题
   |
   v
Agent 首次工具选择
   |--------------------------------|
   v                                v
选择 Direct 入口                  选择 Wiki 入口
   |                                |
锁定 Direct only                  锁定 Direct + Wiki
   |                                |
执行 Direct 检索                  自动执行 Direct 检索
                                    + Wiki 导航与证据回溯
```

具体约束如下：

- 首轮只向 Agent 暴露 Direct 入口和 Wiki 搜索入口
- 选择 Direct 后，当前请求锁定为 Direct only
- 选择 Wiki 后，服务端自动先保留 Direct 召回，然后按“搜索页面—读取页面—解析来源—回溯原始证据”完成 Wiki 链路，Agent 无需再手动重复发起 Direct 检索。
- 如果需要引用证据，Agent 不能绕过路由直接回答；系统会要求其先选择检索路径，仍未选择则停止本次回答。

## 3. 优化二：证据如何进入 LLM

### 3.1 两条路径最终都产生原始 Evidence

Direct 检索直接返回原始文档切片。Wiki 链路中的页面、摘要、关系和来源映射只用于导航，不能直接进入最终引用上下文。Wiki 必须在链路末端回溯到原始文档切片，才能得到可引用的 Evidence。

```text
Direct 检索 ---------------------> Direct Evidence ----|
                                                         |
Wiki 页面/关系 -> 来源定位 -> 原始 Evidence ----|-> 证据处理 -> LLM
```

因此，Wiki 只改变“如何找到证据”，不改变“什么可以作为引用”。

### 3.2 证据在进入 LLM 前的处理

证据不会从检索结果直接全量塞入 LLM，而是经过以下步骤：

1. **Direct 证据作为基础集合**

   Direct 召回结果先去重并保留原有顺序，形成回答的基础证据。

2. **Wiki 证据先通过与 Direct 一致的质量规则**

   低于最低分数、内容为空或版本信息无效的结果不能进入上下文。

3. **Wiki 只补充 Direct 中没有的证据**

   系统根据数据范围、文档、版本和切片身份去重。与 Direct 重复的 Wiki 证据不再插入，也不占用 Wiki 补充名额，后续合格证据可以继续补位。

4. **Wiki 使用独立补充配额**

   默认最多追加 3 条 Wiki 证据。Direct 证据不会为 Wiki 腾出固定名额：例如 Direct 已有 20 条且 Wiki 有 3 条合格新证据，最终为 20 + 3，而不是 17 + 3。补充数量可配置，设为 0 时可关闭该机制。

5. **统一通过证据质量门**

   组装后的证据继续参与统一的质量判定。如果需要纠偏检索，新的 Direct 结果会先更新基础集合，然后再按同样的规则重新补充 Wiki 证据。

### 3.3 证据如何组装成 LLM 上下文

通过质量门后，Direct 与 Wiki 证据会形成一个最终有序列表：

```text
最终 Evidence 顺序 = Direct 证据原顺序 + Wiki 新增证据顺序
```

系统会为每条证据生成连续编号，并连同标题、来源标识、切片内容和检索分数，统一放入一个 `[AUTHORITATIVE_EVIDENCE]` 区块。

最终答案生成时，LLM 收到的核心上下文是：

```text
系统回答规则
+ 用户问题（必要时包含改写后的独立问题）
+ 回答风格
+ 唯一的 [AUTHORITATIVE_EVIDENCE] 证据区块
```

检索阶段的工具调用历史不再作为多个重复证据块交给回答模型。这样可以避免 Direct 证据重复注入，也减少 Wiki 导航中间信息对最终回答的干扰。

### 3.4 LLM 回答与前端引用如何保持一致

LLM 使用证据区块中的编号生成 `[N]` 引用。最终返回给调用方的 Evidence 列表、回答格式化和引用校验继续使用同一个有序证据列表。因此：

- LLM 看到的第 N 条证据，就是前端 Citation 中的第 N 条证据。
- Wiki 页面和关系元数据不会被误当成可引用来源。
- 对外的请求、响应和 Citation 结构不需要改变。

## 4. 整体效果

### 降低 Wiki 的无效调用

简单精确问题可以只走 Direct，只有需要扩展发现范围的问题才启动 Wiki，从而控制检索延迟和 Token 成本。

### 提高 Wiki 新证据的利用率

合格的 Wiki 新证据使用独立补充位，不需要与已有 Direct 证据重新争夺同一配额。

### 保持证据和引用边界

Wiki 仍然是导航层，原始 Evidence 仍然是唯一引用权威。本次优化只改变 Agent 内部的路由和证据组装，不改变上层接口。

## 5. 兼容与降级策略

- 关闭 Wiki 时，系统保持原有 Direct 检索行为。
- Wiki 未返回有效证据时，Direct 结果仍可继续使用，但必须通过统一质量门。
- Wiki 补充数量可设为 0，便于回滚、对照试验和分阶段发布。
- 本次未引入新的分数 boost 或新的 reranker，优化重点是路由、证据进入机制和上下文管理。

## 6. 验证结果

本次实现已覆盖检索路由、Wiki 启动与禁用、Direct + Wiki 联合检索、Wiki 证据去重与补位、质量过滤、权威证据顺序和引用映射一致性等场景。

- Agent 测试：401 项通过。
- Python 编译检查：通过。
- 公开请求和响应契约：保持不变。
- Git 差异格式检查：通过。

以上结果证明代码级逻辑和兼容性已完成验证。上线后的 Wiki 实际触发率、端到端延迟和 Token 变化，仍建议通过灰度流量持续观测。

## 7. 总结

本次优化将 Wiki 从“Direct 证据不足时的事后补救”调整为“Agent 在检索前按问题需要选择的检索路由”，并用独立配额将 Wiki 发现的高质量原始证据补充到最终上下文。

整体架构同时兼顾了检索成本、召回范围、证据可用性和引用可信性，并为后续根据真实流量优化路由策略保留了清晰的扩展点。
