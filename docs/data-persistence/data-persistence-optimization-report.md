# Data Persistence 层优化工作报告

**项目：** AI-QA-Assistant
**分支：** `optimization`
**报告日期：** 2026-09-30
**工作范围：** 持久化边界收敛、文档与向量数据安全、主题产物职责拆分、跨层调用治理及配套改进

## 一、工作摘要

本轮工作的核心目标，是让 Data Persistence 从一组被其他层直接引用的底层存储实现，收敛为职责清楚、入口稳定的模块。Agent、Toolset、Data Pipeline、Attachment Service、Eval 和前端文档删除流程逐步改用 `data_persistence` 对外接口；路径解析、存储访问和向量删除等细节归属持久化层。与此同时，补强文件路径与删除输入校验，并将主题摘要的业务编排从存储代码中拆出。

完成后，业务层可以通过按领域划分的接口访问聊天、文档、主题、向量和 Wiki 能力，减少对 `storage.*` 内部实现的依赖。文档删除流程增加了边界检查、批量向量删除和部分失败反馈。

## 二、改造前的问题

1. 多个上层模块直接从 `storage.*` 导入实现类和函数，存储目录结构成为跨模块隐式接口。底层文件移动或重构会牵动 Agent、Toolset、Pipeline、Attachment 与评估代码。
2. 文档目录和路径拼接逻辑散落在调用方，文件 ID 与文件系统路径边界缺少统一防护，增加路径穿越、符号链接逃逸和不同模块行为不一致的风险。
3. 主题摘要、模型调用、结果解析与主题产物写入耦合在 persistence 服务中，业务编排与存储职责不够内聚。
4. 文档批量删除需要多次执行向量删除；前端和后端对失败、损坏元数据及部分完成状态的表达不够明确。
5. 部分兼容入口在导入时可能加载并不需要的实现，增加初始化开销和模块间耦合。

## 三、主要优化内容

### 3.1 建立稳定的领域接口

新增 `data_persistence` facade，并按领域拆分入口：

| 接口模块 | 职责 |
| --- | --- |
| `data_persistence.chat` | 聊天历史等会话持久化访问 |
| `data_persistence.documents` | 文档目录解析、文档保存和访问 |
| `data_persistence.topics` | 主题产物的读取和持久化 |
| `data_persistence.vector` | 向量存储与共享过滤能力 |
| `data_persistence.wiki` | Wiki 持久化访问 |

各调用方通过这些公开入口依赖持久化能力，不再依赖底层模块的文件布局。旧的 `storage` 包级导出采用惰性加载，以兼容现有入口并减少无关模块的导入成本。

### 3.2 收敛跨层 storage 访问

将 Agent、Toolset、Data Pipeline、Attachment Service、评估脚本及相关测试中的持久化导入迁移到 `data_persistence` 接口。文档目录由共享路径解析入口提供；向量过滤函数和 Wiki/文档/向量访问也经由领域 facade 暴露。

迁移后对 Python 运行时代码进行全仓搜索，未发现持久化模块之外仍直接引用 `storage.*` 的运行时导入。该检查用于确认边界迁移情况，不等同于运行时集成测试。

### 3.3 加固文档文件访问

- 集中解析文档数据目录，减少调用方重复拼接和自行推导路径。
- 对文档 ID 和目标路径执行输入校验及目录边界校验，防止路径穿越。
- 在文件访问中考虑符号链接和非普通文件等边界，避免通过路径解析绕过根目录限制。
- 写入使用临时文件后原子替换，降低进程中断时留下半成品文件的风险。
- 删除前校验目标地址，限制操作落在允许的文档存储范围内。

### 3.4 分离主题摘要编排与持久化

将主题产物存取集中到 `TopicArtifactRepository`，经 `data_persistence.topics` 对外提供；将模型调用、内容解析和摘要业务流程移至 Agent 的 `TopicSummarizationService`。API 路由使用请求级依赖创建服务，并通过响应模型明确接口结构。

迁移保持外部响应字段 `soul_content` 与落盘字段 `soulContent` 的既有约定，避免因内部模型或文件组织调整而改变对外契约。原 persistence summarizer 实现已移除，避免业务逻辑存在两份实现。

### 3.5 强化文档删除与向量清理

- 对删除请求中的文档 ID 做类型、长度、路径分隔符、空值和数量限制，并去重。
- 使用参数化进程参数和 JSON 输入传递待处理 ID，避免把用户输入拼接进脚本命令。
- 临时脚本使用受限权限并在完成后清理。
- 文件清理检查真实路径是否位于文档根目录之内，并处理符号链接、非普通文件及缺失或损坏的地址信息。
- 新增向量批量删除接口，将一批 ID 合并为一次安全构造的 Milvus 删除表达式；单条删除接口复用批量实现。
- 对单项清理失败保留明确结果，前端显示部分成功/失败并刷新列表，避免把不完整清理误报为全部成功。

这一删除过程采用逐项清理和结果汇总，提供可诊断的部分失败信息；跨文件系统、索引和向量库的整体事务回滚仍不在本轮范围内。

## 四、预期收益

### 架构与可维护性

- 形成统一、可发现的持久化公共入口，降低跨层对内部目录结构的依赖。
- 将路径、存储和领域编排责任放回各自所属层，提升模块内聚性。
- facade 使后续替换底层存储或调整目录结构时，影响集中在持久化模块及其适配层。

### 安全与稳定性

- 统一文档路径解析及 ID 校验，降低路径穿越和符号链接逃逸风险。
- 原子文件替换可减少中断写入造成的文件不完整问题。
- 安全序列化向量删除 ID，减少构造过滤表达式时的注入风险。
- 前端能够识别部分失败，降低用户对清理结果的误判。

### 效率

- 批量删除减少向量数据库往返次数。
- 惰性兼容导出避免导入未使用存储实现。
- 统一路径和过滤接口减少重复逻辑及后续维护成本。

## 六、已知限制与后续关注

1. 前端删除涉及原始文件、sidecar、BM25 与 Milvus 等多个资源，当前通过校验、逐项处理和部分失败反馈提升安全性与可诊断性，但不是跨资源事务；失败后需要根据返回结果进行补偿或重试。
2. 删除流程继承了现有子进程超时限制。若大量数据处理耗时超过限制，可能出现请求中断；可在后续根据实际规模评估异步任务或可恢复的删除作业机制。
3. Toolset 等独立运行入口仍依赖项目既有的 Python 导入路径配置，需要部署环境保持相应路径配置正确。
4. 本轮没有运行测试和构建；应在具备完整依赖的 CI 或开发环境执行对应验证，重点覆盖路径边界、符号链接、批量删除、持久化 API 兼容和主题摘要端到端流程。
